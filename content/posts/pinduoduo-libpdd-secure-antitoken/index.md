> **负责任披露说明：** 本文是 Type B 分析/综述，不是拼多多现行版本的一手逆向报告。文中不提供 anti-token 生成器、可复用密钥、字段序列、函数偏移、请求模板或绕过风控步骤，也不建议把公开材料用于模拟客户端、批量请求、营销作弊或规避平台处置。

## 〇、摘要：先把四个等号擦掉

围绕拼多多 `libpdd_secure.so` 与 `anti-token` 的公开讨论，最容易出现四个过快的等号：

```text
发现环境记录 = 每次请求全量采集
环境记录较丰富 = 得到稳定设备 ID
客户端 anti-token = 服务端设备画像
还原历史封装 = 还原现行风控
```

这四个等号都不成立。

本文重新对照三组材料：拼多多 2025 年生效的官方隐私政策、看雪对历史 `libpdd_secure.so` 7.80 样本（并提及当时 7.85）的公开分析，以及 2026 年 7 月发布的 `anti-token` 分析。能够相互支持的结论很窄：**某些历史 Android 样本确实在 Native 层组织过系统、Build、网络、SIM 状态、时间与随机量等环境记录，并经过结构化封装与保护后输出。**

但客户端可见材料不能回答：某字段在什么业务事件采集、是否命中缓存、失败时如何表达、服务端如何验真、怎样跨版本归并、与账号和订单如何关联、最终阈值是什么。拼多多官方政策同样只披露可能处理的数据类别和用途，并明确设备信息“具体以实际收集情况为准”。

本文的核心贡献不是再抄一份字段表，而是建立一条克制的解释链：

1. 把公开材料拆成**官方披露、历史样本观察、架构推断**三种证据；
2. 将 anti-token 定义为**事件附近的环境证据包**，而不是天然稳定的设备编号；
3. 说明设备画像与业务风控只能在服务端通过历史、关系和反馈形成，公开客户端逆向看不到这一层；
4. 给出面向防守方的版本治理、请求绑定、数据最小化与分级处置建议。

- 本文没有可独立核验的 APK 来源渠道、完整包名版本元数据、APK/SO SHA-256、ABI、测试设备、Android 构建号、抓取时间与工具版本。
- 7.80 与 7.85 的关系来自原帖作者陈述；本文没有取得两个二进制做差分。

- 文中的服务端管线是 B 级防守架构映射。除非明确标注“官方确认”，否则不代表拼多多生产实现。

## 二、引言与背景：为什么一个购物 App 需要环境证据

> 设备环境只有放进业务事件才有意义。同一台手机浏览商品、领取新人权益和修改收货地址，设备没有变，风险语义却完全不同。

### 2.1 规模让误放与误伤同时变贵

PDD Holdings 官方披露的 2025 年全年收入为人民币 4,318.457 亿元，其中包括在线营销和交易服务。这个数字是集团口径，**不能当作拼多多 App 的用户数或单产品收入**；它只说明相关商业系统处在需要规模化治理的量级。当前官方材料没有给本文一个可直接使用、同口径的拼多多 App DAU/MAU，笔者不拿旧年度活跃买家数冒充 2026 年指标。

电商安全面对的是两边都昂贵的错误：放过批量注册、营销权益滥用、账号接管或异常交易，会形成直接损失；把共享设备、换机、系统升级、弱网或无 GMS 设备当成攻击，又会伤害真实用户。于是单个稳定 ID 并不够，系统更需要回答：

> **这次动作由怎样的安装与运行环境发起，它与哪些历史账号、活动、订单、地址和支付关系相连，风险高到需要增加多少摩擦？**

### 2.2 官方披露给出类别，不给出包格式

[拼多多隐私政策](https://www.yangkeduo.com/pdd_privacy_policy.pdf)在“保障账户及交易安全”场景中列出账户、交易、设备与日志等信息，用于判断账户及交易风险、验证身份、检测和防范安全事件。设备类别包括应用与版本、Android ID、OAID/IDFA、HarmonyOS OAID、网络环境及部分传感器信息；附录给出更宽的设备信息定义，同时明确“具体以实际收集情况为准”。

这里至少有三个限制词：

- **可能会**：不是每个事件必然执行；
- **包括**：说明类别范围，不等于线上的固定字段顺序；
- **具体以实际收集情况为准**：权限、系统、版本、渠道和功能场景都会改变可得性。

政策还给出一个非常有价值的版本锚点：IMEI 仅限 6.63.0 之前版本的拼多多 App。这个锚点比“设备信息很多”更重要，因为它公开证明了采集面会随版本和平台限制改变。

### 2.3 必要信息、风控信息与附加功能不是同一集合

国家网信办发布的《常见类型移动互联网应用程序必要个人信息范围规定》把网上购物基本功能的必要信息列为注册手机号、收货信息和支付信息。设备风控信号可能有合法的安全目的，但不能因此自动变成“浏览商品所必需的全部信息”。工程上仍要区分处理目的、触发场景、保留期限和用户权利。

换句话说，安全不是一张可以无限扩展的字段通行证。字段越多，碰撞和漂移问题不一定越小，合规、解释和泄露成本却会稳定上升。

## 三、客户端分层：历史样本里究竟看到了什么

> 两篇帖子最有价值的共同点，不是某个偏移或密钥，而是它们把“环境观察”和“包的外观”分开了。环境先形成记录，记录再被组织和保护；输出字符串只是最后一层外衣。

### 3.1 第一层：环境观察值

看雪的 7.80 样本分析使用模拟执行与 Native 侧观察，报告了系统属性、Build、网络与 SIM 状态、时间及随机量等记录。原帖作者同时称，当时 7.85 与 7.80 的总体算法结构接近。2026 年的 `anti-token` 帖则从一个动态注册的 Native 入口继续讨论记录拼装、缓存与动态字段。

本文只保留下列**类别级**结论：

| 信号类别 | 公开材料支持到哪里 | 不能外推什么 |
|---|---|---|
| 系统与 Build | C 级历史样本观察到相关记录；A 级政策披露设备/系统类别 | 当前版本必然使用同一属性集合或顺序 |
| App/运行环境 | A 级政策披露应用列表、应用版本等类别 | 每次启动扫描全部应用，或结果直接决定封禁 |
| 网络与 SIM 状态 | C 级历史样本观察到网络/运营商状态类记录；A 级政策披露网络环境 | 能由这些记录唯一识别物理设备 |
| 时间、随机量与会话动态量 | C 级帖子观察到动态记录 | token 本身应长期稳定，或可以跨请求复用 |
| 传感器 | A 级政策列出加速度、重力等类别 | 两篇历史样本已证明每次都读取完整传感器集合 |
| Android ID/OAID 等标识 | A 级政策披露相关类别并给出 IMEI 版本边界 | 它们始终可得、不可重置，或被当作唯一主键 |

这张表故意没有“字段大全”。字段名只有同时带上来源、版本、权限与采集事件才有解释力；离开这些元数据，列表越长，误导性越强。

### 3.2 第二层：记录与封装

历史帖子把原始内容描述成由多条小记录组成的结构。7.80 分析还观察到一条由 Gzip、AES 与 Base64 构成的结构级处理链。这里可以安全得出两点：

1. 内容不是把所有字符串简单拼接后裸传；
2. 包格式有自己的记录规则与版本语义。

但算法名称本身几乎不提供服务端安全保证。压缩解决体积和冗余，编码解决可传输表示，加密提高直接阅读成本；只要执行发生在用户控制的客户端，固定在包内的对称材料与逻辑就必须被视为可观察、可版本差分的资产。真正能限制伪造和重放的，是事件绑定、新鲜度、服务端挑战、安装密钥或平台证明等更高层机制，而这些不能由“看到了 AES”自动推出。

### 3.3 第三层：缓存意味着“存在”不等于“每次重采”

2026 年 `anti-token` 帖的公开部分提到记录缓存以及“不刷新时只补动态字段”的行为。由于本文没有复现实验，只能把它记为 C 级观察；但它很好地暴露了一个常见误读：

```text
二进制里存在采集路径
        ↓ 不能直接推出
本次调用执行了该路径
        ↓ 更不能直接推出
本次请求上传了所有可能字段
```

真实实现通常要在性能、功耗、权限与时效性之间折中。Build 型信息变化慢，网络和时间变化快，传感器可能只在特定场景触发；某项读取失败还可能被表示为空、缺失、错误或沿用缓存。这四种状态在服务端的含义完全不同。

### 3.4 第四层：输出是证据包，不是设备身份证

一个输出若包含时间、随机量或会话上下文，它就可能在相邻调用间变化；若其中又混入相对稳定的系统属性，它仍可以帮助服务端比较环境连续性。于是更准确的命名是：

> **anti-token 是一次调用附近的、版本化的环境证据包。**

它可以承载“这次客户端声称看到了什么”，却不能单独证明：

- 声明一定来自未篡改的官方 App；
- 字段一定由真实硬件产生；
- 两个不同 token 必然来自不同设备；
- 两个相似环境必然属于同一个人；
- 服务端会按客户端字段逐项等权判断。

把“token”翻译成“稳定 ID”是语言带来的错觉。包裹上可以写寄件地址，但地址不是收件人的身份判决。

## 四、越过网络边界：画像和风控为什么不能从 SO 里读出来

> 到这里会遇到一个不太令人满足的答案：客户端逆向越完整，越应该承认服务端未知。因为画像不是一个隐藏在 SO 里的函数，而是跨时间、跨事件的状态系统。

以下内容是 B 级架构映射，用来说明“合理的服务端还需要什么”，不是拼多多内部架构披露。

### 4.1 接入层先处理版本、来源与新鲜度

服务端不能收到字符串就开始算相似度。它首先需要知道协议代际、App 版本、渠道、ABI、采集结果的缺失语义，以及证据是否与本次业务动作绑定。否则旧客户端、灰度包、权限被拒和主动伪造会被混成同一种异常。

防守方更应把解析结果表示成带来源的观察：

| 观察 | 必要元数据 |
|---|---|
| 某系统属性 | 读取方式、App/OS 版本、读取时间、成功/失败状态 |
| 某可重置标识 | 作用域、用户选择、重置可能性、用途 |
| 某网络状态 | 采集时刻、网络类型、精度与变化窗口 |
| 某完整性声明 | 签发方、绑定内容、新鲜度、验证结果 |

Android 10 官方隐私说明列出了对 IMEI、序列号等不可重置标识的访问限制，并建议无须硬件标识的场景改用可重置标识。这与拼多多政策中的 IMEI 历史版本边界方向一致：**标识符不是常量，平台规则本身就是版本轴。**

### 4.2 设备画像是概率归并，不是某一字段落库

一个可解释的画像系统至少要同时处理四类结果：

- **召回**：当前环境像哪些历史安装或设备候选；
- **碰撞**：不同设备因为同型号、同 ROM、同网络而过于相似；
- **漂移**：同一设备升级系统、换网、重装或改变权限后变得不相似；
- **拆分/合并**：什么时候建立新画像，什么时候只给旧画像增加一条低置信边。

因此“稳定设备 ID”若存在，也更可能是服务端内部的画像句柄，而不是客户端某个字段的直接复制。句柄背后还应带置信度、冲突、创建原因、最近观察时间和老化策略。

### 4.3 业务图谱才给设备信号赋义

电商场景里，设备只是关系图的一个节点。账号、手机号、活动权益、订单、收货地址、支付工具、商家、分享/拼单关系、网络和时间共同决定风险语义。

举个不涉及绕过的例子：一台家庭共享设备登录多个账号可能完全正常；若这些账号在极短窗口内重复触发同一种高价值权益，又共享其他高风险关系，含义才会改变。反过来，一次换机、异地网络或标识符重置，不应单独把老用户变成攻击者。

这也是为什么客户端字段表无法回答“会不会被风控”。处置对象是具体业务动作，不是抽象设备。

### 4.4 最后的输出应该是分级动作

Google 对 Play Integrity 的官方建议也没有把完整性声明当作唯一机制，而是要求与其他信号组合、绑定受保护请求，并采用分级处置。这里引用的是通用设计原则，**不是声称拼多多使用了 Play Integrity**。

对电商系统而言，合理输出可以包括放行、降低频率、限制权益、追加验证、延迟处理、人工复核或拒绝。二元 Allow/Deny 不仅更容易误伤，也会向对抗者暴露清晰的阈值反馈。

## 五、证据边界与常见误读

> 本节专门收拾那些“看起来只差一步”的推断。逆向文章最危险的不是错误函数名，而是把两个不同层级之间的一步想象成已经被证明。

### 5.1 六类结论的断言强度

| 说法 | 本文判断 | 原因 |
|---|---|---|
| 历史样本存在环境记录 | **可支持（C）** | 原始分析给出模拟执行与结构观察 |
| 官方披露设备、网络、传感器类别 | **可支持（A）** | 2025-07-08 生效政策明确列出 |
| 每次调用全量采集全部类别 | **不可支持** | 缓存、权限、场景和“实际收集”为变量 |
| anti-token 是稳定设备 ID | **不可支持** | 包含动态上下文的证据包与稳定标识语义不同 |
| 7.80 的字段顺序、偏移、前缀、密钥适用于当前版本 | **不可支持且高风险** | 高度版本化，也会直接帮助模拟请求 |
| 已知客户端格式即可推导后端模型与封禁阈值 | **不可支持** | 缺少服务端代码、数据、标签、策略与实验 |

### 5.2 隐私政策不是抓包，抓包也不是政策全貌

政策覆盖一个时间段内的产品能力和处理场景，往往故意使用类别表达；单次抓包只覆盖一个设备、权限状态、业务路径和实验时刻。两者可以交叉验证方向，却不能彼此替代：

- 政策里列出传感器，不证明本次请求读取了传感器；
- 样本里没看到某字段，不证明其他渠道或场景永远没有；
- SO 里有访问 API，不证明调用结果离开了设备；
- 输出里有某条记录，不证明服务端保留多久或用于哪个模型。

### 5.3 “能解包”与“能伪造可信来源”之间还有很远

即使历史格式能被理解，也只能说明保密性或混淆成本下降。服务端仍可能使用请求上下文、账号状态、网络侧观察、历史行为、限速、灰度策略和业务反馈。反过来，如果系统只依赖客户端固定秘密，那么再厚的 OLLVM 也只是拖延，而不是信任根。

### 5.4 笔者不建议做的事情

- 不把历史帖子中的前缀、密钥、IV、偏移和字段序列整理成现成生成器；
- 不用模拟环境批量访问真实业务接口；
- 不通过反复试错推断营销或账号处置阈值；
- 不把“售空、失败、验证码”等单一界面现象武断归因为设备封禁；
- 不在缺少版本、渠道与 Hash 时发布“最新版已还原”的标题。

这些做法既越过本文的研究目的，也很难产出可靠结论：线上响应可能同时受库存、账号、地域、实验分桶和服务降级影响。

## 六、版本变化：字段、格式和模型有五条不同时间轴

> “版本没怎么变”通常只描述作者观察到的某一层。App 小版本相近，不代表渠道包相同；客户端格式相近，也不代表服务端权重没变。

### 6.1 公开时间线

| 时间/版本 | 公开材料能确认什么 | 仍然缺失什么 |
|---|---|---|
| 拼多多 App 6.63.0 之前 | 官方政策把 IMEI 使用限定在此前版本 | 具体停止日期、各渠道同步节奏、历史数据保留方式 |
| 2025-07-08 生效政策 | 披露设备、应用、网络、标识符、传感器与日志类别，并注明以实际收集为准 | 某次请求字段、token 协议、后端画像公式 |
| 2025-12-02 / 历史 7.80 样本 | C 级帖子观察到环境记录和 Gzip/AES/Base64 结构 | APK/SO Hash、完整渠道与实验矩阵 |
| 原帖所称当时 7.85 | 作者称总体算法结构与 7.80 接近 | 本文没有二进制差分，不能独立确认“接近”的范围 |
| 2026-07-06 anti-token 帖 | C 级帖子讨论 Native 记录拼装、缓存和动态记录 | 对应 App 版本、完整测试环境、与 7.80/7.85 的谱系关系 |

### 6.2 至少同时记录五个版本轴

| 版本轴 | 为什么重要 |
|---|---|
| App 语义版本/build | Java 调用路径、权限和业务触发点可能改变 |
| Native 二进制 Hash | 同一 App 版本也可能因渠道、热修或 ABI 带来不同 SO |
| 渠道与签名 | 官方商店、厂商商店、灰度包的功能开关可能不同 |
| Android/OEM/ABI | API 可见性、权限、属性值和底层实现会变化 |
| 服务端协议/模型版本 | 客户端不升级，解析规则、特征权重和处置策略仍可更新 |

因此，字段序列、结构偏移、字符串前缀、硬编码材料和函数地址只能作为**带 Hash 的样本注释**。它们不适合成为跨版本知识，更不适合作为文章的主要贡献。

## 七、从防守角度改进：让安全性少依赖“没人看懂 SO”

> 客户端混淆仍有价值，它可以提高批量自动化成本。但若防线的成立条件是字段顺序和固定材料永远保密，那么版本发布的那一刻，倒计时已经开始。

### 7.1 优先级清单

| 优先级 | 当前风险 | 建议 | 预期效果 | 成本 | 可行性 |
|---|---|---|---|---|---|
| P0 | 客户端包被误当授权结果 | 服务端保留最终裁决；证据绑定业务动作、账号上下文与短时新鲜度 | 降低跨事件复用与本地篡改的价值 | 中 | ★★★★★ |
| P0 | 多版本字段混用 | 建立协议/特征注册表：App、SO Hash、渠道、ABI、字段来源、缺失语义都入库 | 避免旧字段污染模型，支持快速回滚 | 中 | ★★★★★ |
| P0 | 固定客户端秘密被长期复用 | 把固定秘密仅视为延迟分析手段；高价值动作使用服务端挑战、安装级密钥或可验证平台声明 | 把信任从可复制代码移出一部分 | 高 | ★★★★☆ |
| P1 | 缺失值被当作攻击 | 区分未授权、不支持、读取失败、未触发、缓存命中与可疑矛盾 | 降低 OEM、旧系统和隐私设置误伤 | 中 | ★★★★★ |
| P1 | 字段越积越多 | 按目的做最小化、精度控制、TTL、访问审计和删除；稳定标识与业务 PII 分区授权 | 降低泄露、追踪和内部滥用风险 | 中 | ★★★★☆ |
| P1 | 单设备分数直接封禁 | 设备画像输出候选、置信度和冲突；再与账号/订单/权益图谱组合 | 降低共享设备和换机误判 | 高 | ★★★★☆ |
| P2 | 响应只有放行/拒绝 | 增加限额、冷却、挑战、延迟、复核和申诉，并记录 reason code | 减少误伤，同时降低阈值泄露 | 中 | ★★★★★ |
| P2 | GMS 能力覆盖不完整 | 将平台证明做成可选强证据，并为无 GMS、HarmonyOS、旧系统设计降级路径 | 提升覆盖率，避免单一供应依赖 | 高 | ★★★☆☆ |
| P3 | 模型只看命中率 | 同时监控漂移、误伤、申诉翻转、特征可用率、隐私成本和渠道差异 | 让风控从“拦得多”变成“损失更低” | 高 | ★★★★☆ |

### 7.2 端上应该提交“可解释失败”

防守 SDK 最容易犯的错，是把所有拿不到的值统一成空字符串。空值可能意味着用户拒绝权限、API 在该系统不可用、调用超时、字段不适用、缓存失效或检测到矛盾。若这些状态在端上被压扁，服务端只能猜，模型最终会把某些 OEM 或隐私偏好学成风险标签。

更稳妥的协议不是增加更多隐藏字段，而是让每个记录带最小必要的来源与状态语义，并让服务端能够按版本禁用有问题的特征。

### 7.3 完整性证明也不是万能设备 ID

Play Integrity 的价值在于让外部平台对 App、设备和请求上下文给出可验证声明，并支持内容绑定与分级处置。它仍不能证明操作者是真人、账号没有被接管、订单意图正常，也不能覆盖所有国内设备生态。

所以正确组合是：平台证明提高某些信号的可信度，环境证据描述当前上下文，画像提供历史连续性，业务图谱解释关系，服务端策略决定摩擦。任何一层独自承担全部责任，都会把自己的盲区变成系统盲区。

## 八、AI 与人类边界：AI 能拆状态机，不能替证据升级

> 2026 年的 `anti-token` 原帖主动说明使用 AI 分析。这是一个值得保留的研究事实，也是一条很好的边界线：AI 可以加快代码理解，却不能自动补齐实验元数据。

### 8.1 AI 适合做什么

🤖 **AI** 适合把大段反编译代码按数据流聚类、识别常见算法轮廓、归纳记录写入模式、生成差分脚本草稿、整理字段来源表，并在文献之间寻找术语对应。面对控制流扁平化时，这种“从指令切换到数据”的注意力转移尤其有效。

本文写作中，AI 也用于资料索引、结构规划和表格归纳。但这些工作只减少阅读成本，不产生新的 A 级或实验级证据。

### 8.2 AI 不能替代什么

🧑‍🔬 **Human** 仍需决定样本是否可信、Hash 是否对应、Hook 是否改变行为、控制变量是否充分、帖子截图是否能复现，以及哪些细节不应公开。更关键的是，人必须阻止下面这种证据跃迁：

```text
AI 识别出算法轮廓
    ≠ 算法已经端到端验证
AI 归纳出字段含义
    ≠ 当前生产版本使用该语义
AI 猜测一个后端用途
    ≠ 厂商内部模型事实
```

### 8.3 本文的人机分工声明

本文没有声称 AI 或笔者运行过拼多多样本。人工研究责任体现为：选择原始来源、规定不披露生成细节、区分事实与推断、保留缺失环境，并在发布前逐项复核链接与断言。若未来补做 Type A 实验，应新增独立文章或版本说明，而不是把新实验悄悄写回这篇综述。

## 十、结论：别问包裹“你是谁”，先问“谁能为它作证”

本文最终保留下来的结论，比“完整还原 anti-token”克制得多，也更耐版本变化：

1. 看雪材料能够作为 C 级证据，支持某些历史 `libpdd_secure.so` 样本存在 Native 环境记录、结构化封装与 Gzip/AES/Base64 处理链；
2. 拼多多官方政策能够作为 A 级证据，支持安全场景中的设备、应用、网络、标识符与传感器类别，并明确 IMEI 的旧版本边界和“以实际收集为准”；
3. 两类材料交叉后，仍只能说明**环境证据包的存在**，不能说明每次全量采集、稳定设备 ID、当前协议或服务端画像模型；
4. 字段顺序、结构偏移、输出前缀、函数地址和客户端秘密高度版本化。没有 App/渠道/ABI/Hash/时间的结论，不应写成“最新版事实”；
5. 真正稳健的防守位于服务端：验证版本与新鲜度，保留缺失语义，以概率方式维护画像，把设备放进账号与交易关系，再做可申诉的分级处置。

逆向的注意力常被最亮的字符串和最深的混淆吸走。但在设备风控里，更值得追踪的是证据责任：客户端能声称什么，平台能证明什么，服务端能观察什么，业务结果又能纠正什么。

最后留下的设计问题不是“还能藏住多少字段”，而是：

> **当所有客户端格式终有一天会被读懂，系统是否仍能说明一次拒绝为何成立，并让一次误伤有路可退？**
